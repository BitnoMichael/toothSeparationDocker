# Анализ `per_class_metrics.csv` (эпоха 62) — что реально тормозит модель

Источник данных: `per_class_metrics.csv`, эпоха 62, validation = 360 сканов,
23 592 960 точек GT. Метрики посчитаны по матрице ошибок, накопленной за всю
эпоху (не по среднему по образцам), поэтому разложение «куда уехали точки»
однозначно.

---

## 1. Короткий вывод

1. **20 молочных классов (FDI 51–85) в validation содержат НОЛЬ точек GT.**
   Модель не предсказывает ни одной точки этих классов (0 false positives).
   Значит метрика по всем 53 классам на этом сплите недостижима в принципе,
   а `mIoU = 0.2456` — это среднее по **33 классам с gt > 0**.
2. **Главная ошибка — не «соседи», а фон.** 65.2 % точек зубов уходит не в
   свой класс; из них **57.5 % уходит в фон** и только 42.5 % — в соседний
   зуб. Модель «съедает» поверхность зубов, объявляя её фоном.
3. **Реже всего страдают третьи моляры** (FDI 18/28/38/48): средний IoU
   0.0006, хотя вес у них максимальный (0.173 — самый высокий из всех).
   Это чистая проблема дисбаланса объёма данных (0.76 % точек зубов).
4. **Веса классов — КОСМЕТИЧЕСКАЯ проблема, а не причина плато.** Доказано
   численно, см. раздел 4. Моя более ранняя формулировка «92 % веса loss
   уходит в пустые классы» была неверной: 92 % — это доля *вектора весов*,
   а не доля *loss*. Исправление.

## 2. Разложение ошибок по классам

### 2.1 Фон (класс 0)

| величина | значение |
|---|---|
| доля в GT | 44.27 % (10 445 203 точек) |
| предсказано как фон | 14 963 475 точек (63.4 % всех точек) |
| IoU | 0.6691 |
| precision | 0.6807 |
| recall | 0.9752 |
| **false positives (точки зубов, названные фоном)** | **4 777 522** |

То есть модель пометила фоном **4.78 млн точек, которые по GT являются
зубами**. При этом настоящего фона она почти не теряет (recall 0.975) —
она «раздувает» класс фона за счёт зубов.

### 2.2 Зубы (32 класса с gt > 0)

|---|---|
| IoU | 0.2323 |

Типичный рисунок: **precision выше recall** (FDI 26: prec 0.702 / rec 0.180;
FDI 16: 0.759 / 0.222; FDI 27: 0.933 / 0.101). Модель умеет назвать зуб,
когда указывает на него, но покрывает лишь ~30 % его точек: остальные точки
зуба уходят соседям или в фон.

## 3. Что из этого следует для метрики из статьи

* В validation **нет ни одного молочного зуба**. Если и в test их нет, то
  оценка «по 53 классам» физически не может превысить ~55 %, а «по присутствующим
  классам» не имеет смысла сравнивать с 89.51 % из статьи, если статья
  считала по другой выборке (в 3DTeethSeg'22 900 пациентов, и дети там есть).
  Это нужно проверить на test и train — см. `diagnose_labels.py`.
* `Test_Hybrid.py` считает mIoU по **всем 53 классам для каждого образца**:
  для взрослого скана потолок = 29/53 ≈ 0.55 (32 зуба верх+низ из 53 классов,
  29 для одного взрослого прикуса). Значит 89.51 % из статьи получены
  **не этим скриптом** — это метрика «по присутствующим классам».
  Финальную цифру надо считать именно так.

## 4. Разбор весов классов: 92 % — это не доля loss

Что было заявлено ранее: «92 % веса focal-loss уходит на 20 классов, у которых
нет данных». Проверка числа:

```
Классов без единой точки: 20 из 53
Доля СУММЫ ВЕСОВ у пустых классов (legacy): 91.6%
Доля LOSS у пустых классов (legacy):          0.0000%
Доля LOSS у пустых классов (present):         0.0000%
Отношение w_present/w_legacy по 33 живым классам: min=11.895927 max=11.895927
  -> КОНСТАНТА: относительные градиенты идентичны, разница только в масштабе.
```

Почему так:

* `FocalLoss.forward` в `Train_Hybrid.py` возвращает `focal_loss.mean()` —
  обычное среднее по точкам, **не** взвешенное среднее;
* вес берётся по истинной метке точки (`alpha[targets]`), у пустых классов
  целевых точек нет → их вес не входит ни в числитель, ни в знаменатель;
* нормализация `weights / sum(weights) * 53` меняет все живые веса на
  **один и тот же коэффициент 11.896**, то есть относительные градиенты
  не меняются вовсе;
* AdamW инвариантен к общему масштабу градиента → траектория обучения
  **идентична**.

Вывод: это артефакт визуализации вектора весов, а не механизм, который
«съедает» обучение. Перезапускать задачу из-за этого не нужно.

Что реально смещено — это **фон против зубов**: фон занимает 44.3 % точек и
39.1 % массы loss при весе 0.1056 (то есть на точку фон «легче» зуба), а
модель при этом всё равно **переоценивает** фон. Значит проблема не в балансе
классов, а в том, что модель не умеет отличить поверхность зуба от фона.

В код добавлен явный режим `--class_weight_mode {legacy,present}`
(по умолчанию `legacy`, поведение текущих запусков не меняется) и разбор
весов в лог обучения.

## 5. Ранжированные гипотезы на оставшийся разрыв

| # | гипотеза | как проверяем | цена |
|---|---|---|---|
| H1 | **Порядок вершин .obj не совпадает с порядком меток .json** (часть разметки «размазана» по геометрии). Тогда резких границ зубов не получить в принципе: модель выучивает только крупные формы — а это ровно то, что мы видим (фон 0.67, зубы 0.17–0.45, «съеденные» поверхности). | `diagnose_labels.py`: count-mismatch `len(.obj)` vs `len(.json)` + kNN-purity разметки + компактность классов | 2–5 мин CPU |
| H2 | **Разметка в порядке, но не хватает разрешения/объёма**: 65 536 точек на скан, модель «замыливает» границы зубов, отдавая их фону и соседям. | увеличить `--num_points` до 131 072 и/или `max_vertices`; сравнить per-class recall | 1 перезапуск |
| H3 | **Дисбаланс редких классов** (третьи моляры, 0.76 % GT). | оценить вклад: без них mIoU +2.0 п.п.; при 89 % целевого IoU их вклад ≈ 2 п.п. — объясняет лишь малую часть разрыва | уже посчитано |
| H4 | **Асимметрия верх/низ** (0.166 против 0.298) — специфика данных/разметки верхней челюсти. | `diagnose_labels.py --splits train validation test`: доля фона и число зубов по челюстям | 5 мин CPU |
| H5 | **Формат GT**: в 3DTeethSeg'22 разметка может отличаться от того, что предполагает репозиторий (например, фон включает небные участки, а в GT зубов записана только коронка). | сверка с оригинальным датасетом (1 кейс вручную) | вручную |

H1 — самая дешёвая и самая разрушительная гипотеза; она проверяется за минуты
и без обучения. **Начинать с неё.**

## 6. Что запустить сейчас (без перезапуска обучения)

```bash
# 1) Проверка разметки и распределения классов по всем сплитам (CPU, минуты)
python diagnose_labels.py --root /app/Dataset_900 \
    --splits train validation test --max-cases 30 --knn 10 \
    --out per_class_distribution.csv

# 2) Численная проверка утверждения про веса (numpy, без torch)
python verify_class_weights.py --csv per_class_metrics.csv
```

Что смотреть в выводе (1):

* `count-mismatch` — если > 0, разметка обрезается в коде датасета
  (`min_len = min(features, labels)`), и это уже баг данных;
* `kNN-purity` — **> 0.5 = разметка согласована с геометрией** (H1 отпадает),
  **≈ 0.05 = разметка случайна** (H1 подтверждена, обучение надо переделывать);
* `молочных (FDI 51-85)` — если 0 во всех сплитах, метрику 89.51 % из статьи
  на этом разбиении получить нельзя, и это надо зафиксировать в отчёте;
* блок «по челюстям» — доля фона в верхних и нижних челюстях (H4).

## 7. Что делать с обучением

* **Перезапуск НЕ нужен** из-за весов классов (раздел 4) и из-за
  `--dump_per_class` (это чистая телеметрия).
* При следующем естественном перезапуске имеет смысл поднять
  `--num_points 131072` (тест H2) — это ~2× времени на эпоху, но прямо
  бьёт по «съеденным» поверхностям.
* Следить за LR-restart'ами: подтверждён рестарт на эпохе 27 (train_loss
  +51 %, val_mIoU → 0.2669), следующий ожидается на эпохе 67.
* Метрика для решений — confusion-mIoU (консультация из 33 классов);
  legacy-mIoU (per-sample) держать рядом как число, сравнимое со статьёй.
